# Ручной прогон seo-pedant

Инструкция агенту. Всё, что считается, считает код — модель интерпретирует и доставляет.

## 0. Пауза

Прочитать `config/pause.json`. Если `paused_until` в будущем — не запускать и сказать об этом.

## 1. Прогон

```bash
npm run audit
```

Если нужен быстрый прогон без браузера и Lighthouse — `npm run audit:fast`.
В выводе последним идёт готовый текст короткого отчёта, он же лежит в `reports/<runId>.slack.txt`.

Прогон считается успешным, если у всех страниц есть вердикты и нет пунктов со `skip` по причине
«нет данных» (кроме тех, что ожидаемы для выбранного режима). Пункт `text-uniqueness-external`
всегда `na` — это норма.

## 2. Интерпретация

Скрипты дают факты. Работа модели — то, чего они не умеют:

1. **Сверить с прошлым прогоном.** Раздел «Устранено» в отчёте — это устранённые проблемы.
   Раздел «Перестало проверяться» — НЕ устранённые: там проверка просто не выполнялась.
   Не путать их в Slack-сообщении.
2. **Отсеять остаточный шум.** Кандидаты: P3 про неудачные запросы к счётчикам (зависит от сети
   машины), P3 «сервер отказался отвечать проверке» (антибот). Если это подтверждённое ложное
   срабатывание — предложить владельцу запись в `config/ignores.json`, не добавлять её самому.
3. **Сгруппировать по причине, а не по странице.** Одна и та же причина на пяти страницах — это
   одна проблема, а не пять.
4. **Назвать вероятную причину**, если она видна из данных. Пример: 420 битых ссылок на
   `/airlines/<код>?language=ru` — это не 420 проблем, а один сломанный шаблон блока авиакомпаний.
5. **Проверить себя.** Прежде чем утверждать, что ссылка битая или тег отсутствует — посмотреть
   на `evidence` в отчёте. Если доказательства нет, формулировать осторожнее.

## 3. Отправка в Slack

Канал — `channel_id` из `config/delivery.json` (сейчас `C08664V7RUH`).
Отправлять текст из `reports/<runId>.slack.txt`, при необходимости сократив.

Пока отправка идёт через MCP-инструмент Slack от имени пользователя. Когда появится Slack App
с bot-токеном, добавится `lib/deliver/slack-app.mjs`; текст сообщения при этом не меняется.

Ссылка на полный отчёт в сообщении валидна только после пуша (шаг 4), поэтому порядок такой:
сначала спросить разрешение на пуш, потом пушить, потом отправлять сообщение.

## 4. Коммит и пуш

**Спрашивать разрешение на каждом прогоне**, пока владелец не скажет иначе.

```bash
git add reports data/history.ndjson
git commit -m "audit: <runId> — <N> находок (P1 <n>), новых <k>, устранено <r>"
git push
```

В репозиторий идут только `reports/` и `data/history.ndjson`. Артефакты прогонов (`data/runs/`)
в `.gitignore`: они нужны локально, чтобы прогонять новые проверки по прошлым страницам.

## 5. Стейт

`state/last-run.json` пишет код — не трогать.
`state/slack.json` — для модели: `thread_ts` последнего отправленного сообщения, чтобы следующий
прогон мог прочитать ответы владельца в треде.

## Границы

- `config/*` правит владелец. Модель может предлагать изменения, но не менять сама.
- `data/history.ndjson` не чистить и не переписывать руками: на нём держится вся история.
- `lib/checks/*` не править молча. Изменение или отключение проверки — предложение владельцу
  с обоснованием, а не тихая правка.
- Утверждать, что в треде нет комментариев, можно только после фактического чтения треда.
