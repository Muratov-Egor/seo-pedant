# Ручной прогон seo-pedant

Инструкция агенту. Всё, что считается, считает код — модель интерпретирует и доставляет.

## 0. Пауза

Прочитать `config/pause.json`. Если `paused_until` в будущем — не запускать и сказать об этом.

## 1. Прогон

```bash
npm run audit
```

Если нужен быстрый прогон без браузера и Lighthouse — `npm run audit:fast`.

В выводе прогона идут два блока, и их достаточно для всей работы:

- **«сводка для агента»** — итоги, находки по видам проблемы, примеры и решения, устранённое,
  что не проверялось. Интерпретировать нужно по ней.
- **«короткий отчёт для Slack»** — готовый текст сообщения, он же лежит в `reports/<runId>.slack.txt`.

**Полный `reports/<runId>.md` читать не нужно.** Он для людей на GitHub: на сотне страниц это
0.4 МБ, больше сотни тысяч токенов за прогон, и ничего сверх сводки он для решения не даёт.
Открывать его стоит только если сводки не хватило под конкретный вопрос — например, нужен список
всех задетых страниц по одной группе. Потерялся вывод — сводку можно получить заново, не ходя
в сеть: `node lib/report.mjs --run <runId>`.

Прогон считается успешным, если у всех страниц есть вердикты и нет пунктов со `skip` по причине
«нет данных» (кроме тех, что ожидаемы для выбранного режима). Пункт `text-uniqueness-external`
всегда `na` — это норма.

## 2. Интерпретация

Скрипты дают факты. Работа модели — то, чего они не умеют:

1. **Сверить с прошлым прогоном.** «Устранено» в сводке — это устранённые проблемы.
   «Перестало проверяться» — НЕ устранённые: там проверка просто не выполнялась.
   Не путать их в Slack-сообщении.
2. **Отсеять остаточный шум.** Кандидаты: P3 про неудачные запросы к счётчикам (зависит от сети
   машины), P3 «сервер отказался отвечать проверке» (антибот). Если это подтверждённое ложное
   срабатывание — предложить владельцу запись в `config/ignores.json`, не добавлять её самому.
3. **Назвать вероятную причину**, если она видна из данных. Пример: 420 битых ссылок на
   `/airlines/<код>?language=ru` — это не 420 проблем, а один сломанный шаблон блока авиакомпаний.
   Группировать по причине сводка умеет сама: одна причина на сорока страницах — одна запись.
4. **Не додумывать за данные.** Утверждать, что ссылка битая или тег отсутствует, можно ровно в
   тех формулировках, что стоят в сводке. Нужны подробности сверх неё — открыть полный отчёт
   и посмотреть `evidence`, но по своей инициативе он не нужен.

## 3. Отправка в Slack

Канал — `channel_id` из `config/delivery.json` (сейчас `C08664V7RUH`).
Отправлять текст из `reports/<runId>.slack.txt`, при необходимости сократив.

Пока отправка идёт через MCP-инструмент Slack от имени пользователя. Когда появится Slack App
с bot-токеном, добавится `lib/deliver/slack-app.mjs`; текст сообщения при этом не меняется.

Ссылка на полный отчёт в сообщении валидна только после пуша (шаг 4), поэтому порядок такой:
сначала коммит и пуш, потом сообщение.

## 4. Коммит и пуш

**Разрешения спрашивать не нужно — ни при ручном прогоне, ни по расписанию.** «Запусти прогон»
означает довести дело до конца: собрать, проверить, отчёты в пуш, сообщение в Slack. Останавливаться
на полпути и спрашивать «пушить?» — не бережность, а недоделанная работа.

```bash
git add reports data/history.ndjson
git commit -m "audit: <runId> — <N> находок (P1 <n>), новых <k>, устранено <r>"
git push
```

В репозиторий идут только `reports/` и `data/history.ndjson`. Артефакты прогонов (`data/runs/`)
в `.gitignore`: они нужны локально, чтобы прогонять новые проверки по прошлым страницам.

## 5. Стейт

`state/last-run.json` пишет код — не трогать.
`state/slack.json` — для модели: `thread_ts` последнего отправленного сообщения, чтобы следующий
прогон мог прочитать ответы владельца в треде.

## Прогон по расписанию

Кроме ручного запуска есть облачная рутина: каждый день в 6:00 (Europe/Belgrade)
изолированная облачная сессия клонирует этот репозиторий, гоняет прогон и шлёт отчёт
в Slack. Спрашивать разрешение на пуш и на отправку там не нужно — владелец дал его,
заводя расписание. Всё остальное из «Границ» действует так же.

Отличия облачного окружения от локального:

- **Зависимостей нет.** Перед прогоном нужен `npm ci` и `npx playwright install chromium`.
- **Браузер может не поставиться.** Тогда прогон не отменяется, а идёт `npm run audit:fast`:
  без SSR, консоли, адаптивности и Lighthouse. Отчёт сам пометит эти пункты как
  непроверенные — в Slack про это надо сказать отдельной строкой.
- **IP облачный**, и защита сайта пускает его хуже домашнего. Если страницы отдадут
  заглушку, бот это распознает и пометит прогон неполным: предупреждение из отчёта
  убирать нельзя.
- **Окружение эфемерное.** Всё, что не закоммичено и не запушено, теряется. Поэтому
  `reports/`, `data/history.ndjson` и `state/` пушатся в конце обязательно.
- Ветка репозитория — `master`. Пуш: `git push origin HEAD:master`.

Управление расписанием — https://claude.ai/code/routines

## Границы

- `config/*` правит владелец. Модель может предлагать изменения, но не менять сама.
- `data/history.ndjson` не чистить и не переписывать руками: на нём держится вся история.
- `lib/checks/*` не править молча. Изменение или отключение проверки — предложение владельцу
  с обоснованием, а не тихая правка.
- Утверждать, что в треде нет комментариев, можно только после фактического чтения треда.
