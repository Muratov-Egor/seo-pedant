# seo-pedant

Проверяет страницы aviasales.ru по [SEO Checklist](https://aviasales.atlassian.net/wiki/spaces/EX/pages/6335266859/SEO+Checklist),
сравнивает с прошлыми прогонами и готовит два отчёта: короткий для Slack и полный для репозитория.

Запуск пока только ручной.

## Запуск

```bash
npm install
npx playwright install chromium     # один раз
npm run audit
```

`npm run audit` = `collect` → `check` → `report`. Полный прогон 5 страниц ≈ 4 минуты,
основное время — Lighthouse (2 замера на страницу).

| Команда | Что делает |
| --- | --- |
| `npm run audit` | полный прогон: сбор, проверки, отчёты |
| `npm run audit:fast` | то же без браузера и Lighthouse (≈40 сек) |
| `node lib/collect.mjs --url <url>` | собрать одну страницу, которой нет в конфиге |
| `node lib/collect.mjs --slug countries-tailand` | собрать одну страницу из конфига |
| `node lib/check.mjs --run 2026-07-31` | прогнать проверки по сохранённому прогону, без сети |
| `node lib/check.mjs --run 2026-07-31 --dry` | то же, ничего не записывая |
| `node lib/report.mjs --run 2026-07-31` | пересобрать отчёты |
| `npm test` | тесты проверок на фикстурах |

Отчёты: `reports/<runId>.md` и `reports/<runId>.slack.txt`.
Отправку в Slack и коммит делает агент по `prompts/manual-run.md`.

## Как это работает

```
collect (сеть)  →  артефакты прогона: raw.html.gz, dom.html.gz, console.json, lighthouse.json, …
                       ↓
facts (чистая функция) →  что есть на странице: заголовки, картинки, ссылки, ld+json, текст
                       ↓
checks (чистые функции) →  вердикт на каждый пункт чеклиста: pass / fail / warn / skip / na
                       ↓
run.json  →  diff с прошлым прогоном  →  reports/*.md + *.slack.txt
```

Три следствия этой схемы:

- **Сырые страницы сохраняются.** Новую проверку можно прогнать по прошлым прогонам
  (`node lib/check.mjs --run <старый runId>`) и посмотреть вердикт до того, как она попадёт в отчёт.
- **Проверки не ходят в сеть и ничего не пишут.** Поэтому они тестируются фикстурами.
- **Вердикт, а не только находки.** «Проверено и всё хорошо» отличается от «не проверялось»:
  в отчёте есть и зелёные пункты, и причина, по которой пункт не проверен.

Артефакты прогонов (`data/runs/`) в репозиторий не попадают. История проблем живёт
в `data/history.ndjson` — одна строка на находку на прогон, и только она нужна для
«новое / повторяется / устранено».

## Как добавить проверку

1. Создать файл в `lib/checks/seo/` (или в папке нового семейства):

```js
import { judge } from '../../verdict.mjs';

export default {
  id: 'lang-attribute',
  checklist: 'Атрибут lang у html',   // формулировка пункта чеклиста для отчёта
  family: 'seo-checklist',
  scope: 'page',                      // 'page' | 'site' (site видит все страницы прогона)
  needs: ['html'],                    // нет данных → вердикт skip с причиной, не падение
  severity: 'P3',                     // дефолт, перекрывается severity_overrides в конфиге
  run(f, ctx) {
    if (f.html.lang) return judge([]);
    return judge([{ entity: 'lang', expected: 'атрибут lang задан', actual: 'атрибута нет' }], this.severity);
  },
};
```

2. Дописать импорт и строку в `lib/checks/index.mjs` — порядок в массиве задаёт порядок в отчёте.
3. Добавить в `tests/checks.test.mjs` хотя бы один pass-случай и один fail-случай.
4. Прогнать по прошлым страницам: `node lib/check.mjs --run <старый runId> --dry`.

Значения `needs`: `response` (ответ сервера, есть всегда), `html`, `dom`, `console`,
`mobile`, `lighthouse`, `site` (robots.txt и sitemap), `links` (статусы ссылок).

Проверка возвращает `pass()`, `fail(...)`, `warn(...)`, `skip(причина)`, `na(причина)` или
`judge(находки, важность)`. Находка: `{ entity, expected, actual, message?, evidence?, note?, severity? }`.
`entity` — адрес находки внутри страницы; он входит в отпечаток, поэтому должен быть
стабильным между прогонами (URL без query, а не «картинка №3», и никогда не само значение).

Проверка не ходит в сеть, не пишет файлы и не бросает исключений. Упавшая проверка не рушит
прогон — она становится находкой P3 «ошибка проверки».

## Как добавить страницу

`config/pages.json`:

```json
{ "slug": "countries-tailand", "url": "https://aviasales.ru/countries/tailand", "type": "country", "label": "Таиланд", "enabled": true }
```

`slug` менять нельзя — он входит в отпечаток находки, переименование обнулит историю по странице.
`enabled: false` временно исключает страницу.
`keywords: ["..."]` перекрывает автовывод ключевых слов из URL.

Новый тип страниц: добавить `config/page-types/<type>.json` (наследует `_default.json`).
Если файла типа нет, берётся `_default`, а в отчёте у страницы появляется пометка «настроек типа нет».

## Конфигурация

| Файл | Что задаёт |
| --- | --- |
| `config/pages.json` | список страниц |
| `config/page-types/_default.json` | пороги: длина title, лимит проверки ссылок, минимальная оценка Lighthouse и т.д. |
| `config/page-types/<type>.json` | переопределения для типа страниц, отключение проверок (`checks.disabled`), важность (`checks.severity_overrides`) |
| `config/scope.json` | наши домены (внутренняя ссылка vs внешняя) и временные лимиты проверки ссылок |
| `config/delivery.json` | канал Slack, репозиторий и ветка для ссылки на полный отчёт |
| `config/ignores.json` | подтверждённые ложные срабатывания |
| `config/pause.json` | `paused_until` — прогон не стартует |

### Ключевые слова

Выводятся автоматически, сравниваются по стему — чтобы падежи не мешали («турци» находит
и «Турцию», и «Турции»).

- **Тема** — из первого сегмента пути: `countries` и `cities` → «авиабилеты», `airports` →
  «аэропорт», `airlines` → «авиакомпания». Новый тип страниц — новая строка в `TOPIC_BY_SEGMENT`.
- **Название** — из последнего сегмента обратной транслитерацией. Из слага выбрасываются
  IATA-коды и служебные английские слова, иначе получалась бы бессмыслица:

| URL | Ключевые слова |
| --- | --- |
| `/countries/tailand` | авиабилеты, таиланд |
| `/cities/moskva-mow` | авиабилеты, москва — код `mow` отброшен |
| `/airports/zhukovsky-international-airport-zia` | аэропорт, жуковский — отброшены `zia`, `international`, `airport` |
| `/routes/mow/aer` | авиабилеты, **Москва, Сочи** — названия в URL нет, взято из `label` |

У маршрутов в URL только коды, поэтому название берётся из поля `label` в `config/pages.json`
(«Москва — Сочи»). Если нет ни названия в URL, ни `label`, остаётся только тема: выдуманных
слов не появляется.

Одиночная `y` в транслите разбирается по соседям — на конце после согласной это «ий»
(`zhukovsky → жуковский`), между согласными «ы» (`krym → крым`), иначе «й».

Перекрыть автовывод: поле `keywords: ["..."]` у страницы в `config/pages.json`.

### Внутренние и внешние ссылки

Это две отдельные проверки с разной важностью, и в отчёте они идут разными пунктами:

- `links-internal` — ссылки на наши домены из `config/scope.json` (`aviasales.ru`, `aviasales.ge`,
  `aviasales.uz`, поддомены учитываются автоматически). Битая такая ссылка — наш баг, **P1**.
- `links-external` — все остальные. Битая — сломано на чужой стороне, **P2**. Плюс требование
  `rel="nofollow"`.

Новый наш домен = одна строка в `own_domains`. Атрибут `rel` проверяется у всех ссылок:
для этого сеть не нужна, поэтому лимиты на проверку доступности его не касаются.

### ⏳ Ограничение на время разработки

Сейчас в `config/scope.json` стоит `development.enabled: true`: внутренние ссылки проверяются
**не все, а первые 10 на страницу**, чтобы отчёты не спамили сотнями однотипных находок. Внешние
проверяются полностью. Пока флаг включён, оба отчёта печатают напоминание об этом, а недопроверенные
ссылки не превращаются в находки.

Снять ограничение: `development.enabled: false`.

## Что бот знает про свои ограничения

- **Уникальность текста по всему интернету не проверяется** — нужен платный API-ключ text.ru.
  Пункт помечен `na`, а не «пройден». Дубли между проверяемыми страницами проверяет `uniqueness`.
- **Оценка Lighthouse шумит на ±10** между прогонами на одной странице. Поэтому оценка не входит
  в отпечаток находки: важна тенденция, а не отдельное значение.
- **Защита от ботов сильнее проверки ссылок.** На странице ~400 ссылок, и aviasales.ru отвечает
  на часть проверок заглушкой WAF (HTTP 202) вместо страницы. Такие ссылки не признаются ни живыми,
  ни битыми: они идут одной находкой P3 на страницу с числом и примерами. То же для 401/403/418/429
  от внешних сайтов. Темп проверки снижен (4 потока, пауза 120 мс) — на восьми потоках без паузы
  защита блокировала весь следующий прогон.
- **Если вместо страницы пришла заглушка защиты, бот отказывается судить страницу.** Все её пункты
  становятся `skip`, отчёт печатает предупреждение «прогон неполный», а вчерашние проблемы попадают
  в «перестало проверяться», а не в «устранено». Без этого заблокированный прогон выглядел бы как
  «всё сломалось, зато прошлое починили».
- **Ошибки консоли зависят от сети машины.** Если DNS блокирует счётчики (`mc.yandex.ru`,
  `sp.aviasales.ru`), появятся P3 про неудачные запросы, которых на чистой сети нет.
  Такие срабатывания глушатся через `config/ignores.json`.
- **Alt-теги** проверяются на наличие, непустоту и длину 2–5 слов. Требование чеклиста писать alt
  транслитом не проверяется: на страницах alt по-русски, и буквальная проверка зафейлила бы все картинки.
- **Проверки контента идут по конечной странице.** Если URL из конфига редиректит, редирект
  становится находкой `http-status`, но остальные проверки смотрят на страницу, куда привёл редирект.

## Структура

```
config/           настройки, правит владелец
lib/collect/      сеть: http, robots+sitemap, статусы ссылок, браузер, Lighthouse
lib/facts.mjs     HTML → факты (единственное место, знающее про разметку)
lib/checks/       проверки, по файлу на пункт чеклиста; реестр — index.mjs
lib/collect.mjs   CLI: собрать артефакты
lib/check.mjs     CLI: прогнать проверки, посчитать diff с прошлым прогоном
lib/report.mjs    CLI: собрать отчёты
data/runs/        артефакты прогонов (локально, не в репозитории)
data/history.ndjson  история находок по отпечаткам
reports/          отчёты
tests/            фикстуры и тесты
prompts/          инструкция агенту на ручной прогон
```
